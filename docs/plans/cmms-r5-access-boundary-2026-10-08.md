Status: **Discovery for owner and independent Security review; scope gate remains closed.** This is a source-path assessment, not a demonstrated exploit, an authenticated HTTP certification, or permission to deploy.

## Outcome and frozen route denominator

A CMMS-only customer must be able to assign a maintenance role at a site or unit and know that every reachable read, write, derived result and background effect stays within that assignment. A permission from a second assignment must never inherit the first one's scope. A shared reference record must have an explicit policy. FR-14/15 and NFR-SEC-001 apply; ADR-0034 §1, ADR-0018 §2–3 and the platform plan D6/R5 are the design baseline.

The deployed module's `module.yaml` generates **50 gateway route templates, 72 method-to-permission mappings** (27 GET, 27 POST, 11 PATCH, 5 DELETE, 2 PUT), under `/api/cmms`. The source of this denominator is `apps/workflow-platform/lib/generated/module-gateways.ts`, entry `physical-operations-cmms`; the BFF dispatch is `app/api/[gateway]/[...path]/route.ts`. The following groups partition those 50 templates; each proposed implementation slice must reconcile its paths against the generated routes and mounted controller rather than using the count as proof of security.

## Cross-module and control-plane boundary

1. **The explicit scope gate is correctly closed today.** `SCOPE_ENFORCING_MODULES` is `{}` and `PER_ASSIGNMENT_SCOPE_MODULES` is `[]` in `assignment-scopes.ts`. CMMS consumes the unioned `granted_scopes` and legacy `org_scope`/`spatial_scope` in `auth/authorization.ts:115–181`; it does not decode assignments or call `scopeFor`. Its `scopePredicates` allows null-department shared reads, compares place IDs exactly and does not expand place descendants (`auth/scope.ts:10–46`). CMMS stores `organization` in the principal but no mounted service consumes the tree version or roots. Before unit access, add a versioned organization projection and fail closed when the required version is absent; T3 supplies the canonical place directory/descendants before place access.
2. **Bundled roles prevent truthful narrow scope.** All three CMMS default roles carry `maps.nodes.read`; technician and planner carry Workforce permissions; planner grants workspace-wide Workforce resource management and time/absence approval. The generated permission catalogue gives `maps.nodes.read` to `asset-maintenance`, `geospatial` and `platform`. `explicitScopeRefusal` refuses any platform consumer and any unproved module. The web's `punch-geofence.ts:61` is a platform consumer. `geospatial-studio` versus `geospatial`, and `universal-connector-hub` versus `connections`, are separate key-attribution problems. Do not change catalogue ownership by renaming a key alone.
3. **Recommended role composition for decision:** keep CMMS-only maintenance read/execute/manage roles with CMMS permissions; issue Workforce and Maps companion grants only when those modules are entitled and needed. Split planner's Workforce people/time approval from maintenance planning. Treat a CMMS place picker as a narrow read adapter to the canonical place identity, with server-side scope/entitlement checks, if the customer has no full Maps module. Preserve each existing holder's effective access until an approved migration/cutover and report any gain/loss. Editing current module-role manifests in place would cause `syncDefaultRoles` to rewrite built-in roles in every entitled tenant.
4. **Manifest sync must obey the transition rule.** `tenancy.service.ts:706–777` updates system role permissions and audits them, but does not call `assertScopesConsistent` or `assertScopeEnforced` for current holders, including roles that transitively include the changed role. Add an impact preview, tenant lock, affected-holder walk and all-or-nothing refusal before any scoped CMMS role can be assigned. Keep inclusion expansion and permission-catalogue ownership in that check. The current empty explicit-scope gate contains the widening risk; that containment ends when R5 opens it.
5. **Revocation wording needs reconciliation.** ADR-0034 §4 says a role change bumps a member session version and the next request is refused. As built, `auth.service.ts:540` derives `authVersion` from session creation and the request re-reads current assignments; the module also consults revocation state. Record the actual next-request and old-context behavior with tests before changing an enforcement allow-list. Do not claim the ADR's specific version-bump mechanism is implemented from the current source.

## Required implementation order and acceptance

1. Repair the **currently reachable legacy-scope gaps** first: part issue/return/TCO, storeroom/balance paths, meter trigger/batch paths, space/CAD paths and work-order mutations hidden in Reliability. Protect both source and target records when a command touches two objects. The gateway permission and owning domain permission must agree; any changed grant effect gets an existing-holder compatibility report.
2. Approve the shared/owned entity policy and the CMMS-only versus companion-role design. Review all 50 route templates and mounted internal paths against the matrix after the edits; keep unmounted import/export unavailable.
3. Harden manifest role synchronization and transitive holders before allowing explicit scopes. Build the CMMS unit-tree projection and per-permission `scopeFor` checks for list, direct ID, command, lookup, aggregate and async effect; test stale and missing tree versions. Only then set `SCOPE_ENFORCING_MODULES['asset-maintenance'].units` and `PER_ASSIGNMENT_SCOPE_MODULES` for the proven unit paths.
4. Complete T3's canonical place identity/projection. Then add descendant-aware place enforcement to every CMMS path, including spaces/storerooms/balances and cross-module place reads; only then set the CMMS `places` gate. Other permission consumers remain independently gated; do not open Geospatial/Workforce/Connector or platform access by CMMS proof.
5. Run authenticated two-tenant/two-site tests with a read-only member, approver-in-North/reader-in-South, direct-ID attempts, shared references, mixed part/work-order ownership, stale tree, old signed context, role edit/inclusion/sync/revoke, and job retry. Assert negative responses and unchanged rows/ledger. Reconcile existing members and independent Security review before any owner-run deployment. This discovery slice provides no such test evidence yet.

## Decisions for the owner before Build

- Approve or revise the candidate ownership policies above, especially `EITHER` assets/work orders/parts, shared reference masters, and site-owned spaces/storerooms. Existing null department/site values need an explicit interpretation and migration/compatibility plan.
- Approve separating CMMS core roles from optional Workforce and Maps companion roles, with an access-preserving transition for current holders. The technician's execute-own command stays with M-CM1; no silent new ability to alter any work order.
- Approve the dependency order **R5 legacy-gap repair → R5 unit proof → T3 place identity → R5 place proof → M-CM1** if the customer must have place-scoped access at M1a. The published plan's single R5-before-T3 line cannot prove place descendants before T3 exists.
- Decide whether changing a work order through Reliability/Parts requires both domain permissions or a distinct narrow action permission. Preserve current users until the grant change is reviewed.

No product code, migration, UAT data, entitlement, role or scope gate was changed in this discovery slice. Production remains NO-GO.
