# Operator Inspection Rounds

Generated by `pnpm module:new operator-rounds` (WI-OI-085). A business module on the core module SDK (ADR-0013): its own
API service, schema (`gigalibs_operator_rounds`) and least-privilege role, reached by the web only through its manifest-declared
gateway `/api/operator-rounds` with a platform context the BFF signs for audience `gigalibs-operator-rounds-api`.

The module owns route versions, roster references, assignments, runs, readings, evidence metadata, exceptions and
their audit/outbox records. Keep:
- every route behind `AuthorizationGuard` with `@RequirePermissions('operator-rounds.<area>.<action>')`;
- every statement in `DatabaseService.withTenantTransaction`, and every change followed by `recordMutation`;
- forward-only migrations listed in `db/runtime-manifest.txt`, each table with forced RLS on `app.tenant_id`.

## Route schedule and roster

A published route stores its cadence, IANA time zone, local start, assignment window minutes and grace minutes.
The separate `route_rosters` table holds at most ten Workforce resource/user references per published route, with
an optimistic version. `POST v1/routes/{id}/roster` replaces that list only when `expectedVersion` matches; `GET`
returns the current version. An administrator can call `POST v1/routes/{id}/generate` for one local date and that
roster version. Daily routes run every day; weekly routes run only on selected ISO weekdays. The service refuses
nonexistent daylight-saving wall times and chooses the earlier instant when a time repeats. Every occurrence uses
a deterministic request key, rechecks the current roster version immediately before insertion, and asks Workforce
to verify position, working slot, absence and site closure. The result names each accepted/replayed or failed
operator so a partly successful request can be retried safely. Generation is bounded to 10 operators and a date
from seven days before through 31 days after the request.

Admin-triggered `PER_SHIFT` generation now asks Workforce for the linked resource's effective-dated working
windows on the route-local date, then passes each window through the same live eligibility and roster-version
checks. A kernel schedule may run route-local daily generation as its current owner; the module skips inactive
weekly dates and asks the worker to retry transient Workforce failures. PostgreSQL/HTTP proof of these paths
remains open. The first build cannot be called complete until those paths and the mobile/offline journey are proven.

Migration 6 is additive. Existing assignment readers and writers remain compatible. The supplied down migration
will run only while no roster rows exist; after configuration is used, recovery is a forward migration. The
roll-forward proof on a disposable PostgreSQL database is recorded in `.pi/work/WI-OI-133.md`.

## Evidence binding and migration 7

`POST v1/evidence` now requires the assignment and checkpoint IDs with the upload digest. The service verifies
operator ownership, execution scope, active assignment and checkpoint membership before creating a staged row;
an exact retry can retrieve its committed result after the assignment closes. Capture accepts a committed photo
only for that same operator, assignment and checkpoint. A partial unique index prevents one evidence ID from
being attached to two readings, including concurrent writes. This contract change is safe before M-RND release;
older staging clients must update before the endpoint can be activated.
Rejected evidence cannot receive another signed upload URL or be reported as committed, including a commit race.

Migration 7 adds nullable binding fields so historical evidence and readings remain readable. Legacy unbound
uploads cannot be attached to new readings. Before applying it to a populated database, check for duplicate
non-null `(tenant_id,evidence_id)` references in `readings`; resolve duplicates with a forward data correction.
The down migration works only before any bound evidence is staged. After use, recovery is a forward correction.
The disposable PostgreSQL clean, empty rollback, roll-forward and forced-RLS proof is in
`db/proofs/000007_evidence_binding.sql`; its result is recorded in `.pi/work/WI-OI-133.md`.
