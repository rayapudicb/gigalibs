# ADR-0039: Cross-module reference integrity — entity events, reference replicas and validation

- **Status:** Accepted by the owner, 2026-11-03 (decision 3 of the analysis §9). Independent Architecture and Security
  reviews pending.
- **Date:** 2026-11-03
- **Work items:** WI-OI-156, WI-OI-160
- **Builds on:** ADR-0018 organization replica, the party relay (WI-OI-146 QA-046), module outbox/inbox relays.

## Context

- Modules hold ids of other modules' records (`product_id`, `uom_id`, customer and vendor ids, warehouse ids) with no
  check that they exist or are active; `product.created/updated/archived.v1` are defined in contracts and never
  published; an archived product stays usable on new documents.
- Module isolation forbids cross-module foreign keys (ADR-0016); the organization replica already shows the safe pattern.

## Decision

1. **Owners publish entity events** through their outbox: `<entity>.created|updated|archived.v1` with a version, for
   every master declared in `spec.masters`.
2. **Consumers keep a reference replica** per referenced entity (id, code, name, status, version, a small payload),
   fed by signed relays into an idempotent inbox, applied by version; a backfill job seeds it from the owner.
3. **The record dispatcher validates references**: a field declared in `spec.references` must point to an existing
   record in the replica, and to an ACTIVE one when the value is new (`onArchive: BLOCK_NEW` by default); unchanged
   values on existing records are not re-checked.
4. **Rollout per module:** backfill → shadow mode (log violations) → enforce, behind a module flag.
5. **Relay wiring is generated from manifests** (WI-OI-160) so producer, relay and consumer keys cannot be configured
   on the wrong service.

## Consequences

- No cross-module foreign keys; integrity is enforced at write time by the consumer.
- Screens can show names from the replica instead of live lookups to other modules.
- Each consumer needs one replica table per referenced master and an inbox handler (generated by WI-OI-159).

## Alternatives considered

- Live validation calls to the owner on every write: rejected — couples availability and latency across modules.
- Cross-module foreign keys: rejected — breaks isolation and per-module schemas.
