# GigaLibs modules: purpose, connections, and outcome integrity audit

Read-only source review on 2026-09-09. Scope: every immediate `modules/*` directory (11), module manifests, registered NestJS services/controllers, selected migrations, source test inventory, architecture ownership ADR, work-item claims, and selected suite BFF routes. No product files, database records, services, or external systems were modified. No runtime certification was executed by this reviewer. Findings describe checked source; deployment exposure and current DB data provenance require root agent runtime evidence. Existing dirty/untracked work was preserved.

## Main conclusion

Database persistence is present in all eleven modules, but persistence does not establish authentic inputs, actual external execution, or a complete business outcome. Several modules explicitly persist fabricated success/results. Workflow orchestration, connector sync/test, recovery scanning/actions, treasury revaluation, data lineage/normalization, and RBAC writes contain concrete misleading behavior. No module can be called fully business-ready from this review. Standalone AR has a materially stronger bounded foundation and candid incomplete/not-certified evidence; that is not certification of the entire AR suite.

All eleven manifests say `lifecycle: implementation`. AR alone has an explicit release evidence index with `humanApprovals: []` and `productionObservation: null` (`modules/accounts-receivable/release/evidence-index.yaml:43`). Other manifests' capability lists are claims, not demonstrations.

## Highest-risk source findings with expected versus actual outcomes

### MOD-001 — P0: Workflow service persists approval/ledger/delivery success without performing the actions

- Source: `modules/workflow-studio/apps/api/src/execution/execution.service.ts:285` through `:349`.
- Trigger: execute persisted workflow containing CONTRACT_VALIDATION, FX_CONVERSION, RULE_DECISION, TAX_CALCULATION, LEDGER_WRITE, APPROVAL_GATE or NOTIFICATION nodes.
- Expected: invoke authorized corresponding module/provider, verify result/receipt, enforce human approval, reject missing or unknown implementation.
- Actual: returns constants/local fabricated identifiers. Approval is always granted, notification always delivered, ledger always COMMITTED; unknown node types succeed too. Output is persisted as COMPLETED at `:89`, and whole run at `:136`.
- Business impact: a real database now contains false attestations of financial, policy and external actions. Every downstream workflow outcome inheriting these steps is untrustworthy. Classified runtime-reachable prohibited behavior in source; deployed reachability pending runtime evidence.
- WI-OI-025 explicitly claims cross-module handshakes (`.pi/work/WI-OI-025.md:37`) and rollback/retry (`:34`), contradicted by implementation.

### MOD-002 — P0: Recovery outcomes are fabricated or asserted by local status changes

- Scanner source: `modules/autonomous-recovery-studio/apps/api/src/scanner/scanner.service.ts:24`. Reads existing leaks only, fabricates records scanned and minimum latency; zero existing leaks fall back to six leaks and $290,290; saves COMPLETED at `:35`.
- Action source: `modules/autonomous-recovery-studio/apps/api/src/leaks/leaks.service.ts:114`. BLOCK_PAYMENT and AUTO_APPLY_CREDIT do not call AP/payment/credit systems, but set HELD/RECOVERED.
- Clawback source: same service `:124`. Sends `{context: ...}` to executor which requires trigger_payload/input_payload (`workflow-studio/.../execution.service.ts:19`), reads `runId` although executor returns `run_id` (`:168`), generates a run ID before dispatch, ignores non-OK response and catches network failure. Then persists WORKFLOW_CLAWBACK_DISPATCHED and that ID (`leaks.service.ts:156`).
- Claims source: `claims/claims.service.ts:69`; caller SETTLED status marks leak RECOVERED without bank/provider evidence. The review must separate human-recorded claims from verified financial recovery.
- No authenticated actor/tenant context or source scanning engine is present in these three services. WI-027 claims real cross-system scanning, automatic holds and financial recovery (`.pi/work/WI-OI-027.md:13`, `:34`) are unsupported.

### MOD-003 — P0: RBAC and usage writes report success after persistence failure

- `modules/platform-rbac/apps/api/src/rbac/rbac.service.ts:317`: failed membership INSERT returns ACTIVE user object.
- `:330`, `:347`, `:360`: failed permission grants/denials/removals and spending-limit updates return success.
- `:617`: usage-record insert and credit decrement are separate writes; exceptions return success at `:630`. No negative-balance predicate accompanies decrement.
- Expected: persistence error must be explicit and retryable, mutations atomic/idempotent, authorization from verified principal; grant/deny must be confirmed effective on protected operations.
- Impact: tenant admins can believe access was removed or limits enforced when nothing was saved; charge/usage evidence can diverge.

### MOD-004 — P0/P1: Connector readiness and sync are invented; webhook receipt lacks advertised signature enforcement

- `modules/universal-connector-hub/apps/api/src/connectors/connectors.service.ts:116`: get DB row, then return READY, schema PASSED and credential ENCRYPTED_VALID with no checks. Stored creation defaults READY/PRODUCTION at `:85`.
- `sync/sync.service.ts:40`: recordsIngested=5, save COMPLETED job and increment counters. No provider fetch or resulting journal records.
- `webhooks/webhooks.service.ts:24`: accepts connection by slug and optional caller tenant; hash at `:45` is payload fingerprint, not keyed signature authentication. No createHmac/timingSafeEqual or HMAC verifier import/call in service.
- Retry loss: first request durably journals, workflow dispatch fails, service returns INGESTED; identical request exits DUPLICATE (`:70`) before dispatch; no retry worker in module. Source does not establish a guaranteed downstream outcome.

### MOD-005 — P0: Missing tax jurisdiction becomes a persisted zero-tax result

- `modules/tax-configuration/apps/api/src/calculate/calculate.service.ts:121` sets appliedRateBasisPoints=0 when jurisdiction is missing. Ledger INSERT commits at `:146`/`:191`.
- Expected unavailable/invalid configuration, no tax result claimed. Test unknown/inactive jurisdictions, stale/ambiguous overrides, negative/unsafe values, concurrent same idempotency key and mismatching payloads. Source review establishes fallback defect without issuing a tax/legal conclusion.

### MOD-006 — P0/P1: Financial reporting and FX data provenance are unsound

- `modules/multi-currency/apps/api/src/revaluation/revaluation.service.ts:24` never uses injected DB; returns fixed assets/liabilities/exposure/gain-loss and CURRENT status for every tenant/date.
- `pairs/pairs.service.ts:67` and `:87` look in caller tenant OR a hardcoded tenant; do not filter rate status/effective date. `hedging/hedging.service.ts:31` shares that tenant's contracts too.
- Conversion arithmetic at `convert/convert.service.ts:99` lacks source/target currency minor-unit exponent adjustment and safe integer validation. Example required test: USD cents into JPY zero-decimal units; numerical formula currently treats them alike. No approved/live provider rate pipeline found within module.

### MOD-007 — P1: Data normalization and lineage claim integration not executed

- `modules/universal-data-studio/apps/api/src/mappings/mappings.service.ts:129`: presence of currency/amount and configuration flag sets currency_normalized=true; neither amount nor currency is converted and no FX service invoked.
- `lineage/lineage.service.ts:25` hardcodes SAP/Plaid/Salesforce/ECB and downstream modules/handshakes; queried contract/mapping rows do not establish these connections. An empty tenant receives the same hardcoded graph.
- Expected lineage edges from actual authorized connection/version/event records; normalized=true only after real documented conversion.

### MOD-008 — P1: Rule/validation semantics can accept data contrary to the advertised policy

- Rule department branch is empty (`universal-rule-pro/.../evaluator.service.ts:60`); selection ignores effective dates; audit match is fire-and-forget (`:80`) and no-match evaluations are not recorded.
- Decision-table loop returns first row regardless of table.hit_policy (`decision-tables.service.ts:59`, `:79`).
- Data validator does not recurse schema/nested fields; unsupported assertion kinds fall through with passed=true (`universal-data-studio/.../validation.service.ts:95`); range checks on Number(value)=NaN do not fail (`:128`). Unknown types, boolean/object/enum/additionalProperties/min/max/nested required need explicit tests. This is a limited validator, not a full JSON Schema engine.

### MOD-009 — P0: Eight standalone module APIs lack verified identity boundaries in inspected source

Tax, currency, data studio, rule pro, workflow studio, connector hub, recovery and platform-RBAC lack OIDC guards in their module API controller/bootstrap registration. Most take tenant from arbitrary header/body/query with a hardcoded default; recovery has no tenant filters at all. Example `universal-rule-pro/.../evaluator.controller.ts:13`; platform admin `platform-rbac/.../platform.controller.ts:4`, app `:11`, main `:7`; recovery `claims/claims.service.ts:11`.

The suite currency BFF independently forwards caller tenant or default without validating a session (`apps/workflow-platform/app/api/currency/[...path]/route.ts:22`, `:42`). Authenticated screen visibility would not secure these direct API paths. Root runtime checks determine actual exposure; do not claim a successful exploit from source alone. AR, spend and CMMS do have OIDC-protected controllers; their effectiveness needs negative/isolation runtime tests.

### MOD-010 — P1: CMMS and spend outbox chains have no located consumers

Repository search for `cmms.meter.reading.ingested`, `gigalibs_cmms.outbox_events`, `gigalibs_spend.outbox_events` across modules/apps/packages/scripts returns producers/schema/docs only. `physical-operations-cmms/README.md:92` claims rule-consumed IoT→emergency work order. Actual separate insert/update/outbox operations at `meters/meters.service.ts:123` can leave partial state. Preventive schedule trigger creates WO before separately advancing schedule at `pm-schedules/pm-schedules.service.ts:128` and `:143`.

External separately deployed consumers could exist but were not supplied/evidenced; classify connected automation as unverified/present but disconnected, not nonexistent globally. Tax/currency outbox tables similarly have no located producers or consumers in scope.

### MOD-011 — P1: Module entitlement hydration does not activate actual module storage

`platform-rbac/.../platform/platform.service.ts:221` and `:290` create only `tenant_{slug}_{module}` schemas, then record entitlements/audit; module APIs query fixed `gigalibs_ar`, `gigalibs_spend`, etc. This does not demonstrate module migrations, health, routing, permissions, jobs, or usable activation. Provisioning's `tenant_*_core` identity store also duplicates ADR authoritative memberships/roles. Staff creation sets placeholder password and MFA enabled unconditionally (`:369`).

## How the modules actually connect in inspected source

1. Approved architecture: `apps/workflow-platform` is primary UI, control plane is `apps/playground-api` + `packages/db`, execution plane is FastAPI; single owner per identity/workflow/audit business concept (`docs/architecture/ADR-0001-operational-intelligence-service-ownership.md:20`). This remains the baseline rather than inventing an alternative desired architecture.
2. New suite BFFs proxy to standalone module daemons; common UI navigation alone is not business integration. Concrete example: currency BFF `apps/workflow-platform/app/api/currency/[...path]/route.ts:29` forwards API requests.
3. Connector webhook→workflow HTTP call is implemented (`universal-connector-hub/.../webhooks.service.ts:111`). That workflow's module actions are fake local returns, so this chain ends at persisted synthetic outcomes.
4. Recovery→workflow call is present but contract-mismatched and failure-tolerant as described above. There is no implemented recovery→payment hold or recovery→credit ledger write in its action service.
5. Data studio lineage is a drawn static relationship graph. Workflow does not call data/rule/FX/tax services despite advertised handshakes.
6. Standalone AR issue→transactional outbox→signed HTTP receiver has actual worker source. The receiver and subsequent business result must still be certified; event delivery alone does not collect payment.
7. Spend/CMMS event producer tables exist; no located dispatcher/consumer closes the loop. Platform entitlements create unrelated empty schemas; there is no demonstrated runtime activation of actual module APIs.
8. Manifests declare all `requiredModules: []` while claiming cross-module outcomes. Optional dependencies are reasonable for standalone bounded CRUD, but required activation dependencies must be enforced for an outcome that needs those modules.

## Governance/claim mismatches

- `.pi/PLAN.md:21` says AR is sole active Build module, while `.pi/WORK_ITEMS.md` lists numerous 019–035 module implementations in Review. Baseline FR-17 and many FRs retain proposed/pending status; root should reconcile status evidence rather than selecting optimistic text.
- `.pi/work/WI-OI-025.md:34`, `:37` claim rollback and real handshakes; source does not implement them.
- `.pi/work/WI-OI-027.md:13`, `:34`, `:43` claims source scanning, true recovery and SLA/ROI dashboard, while source scanner/actions fabricate evidence.
- `.pi/work/WI-OI-035.md:14`/`:19` uses production/compliance language; standalone AR release index remains not-certified with no human approvals and README lists full-outcome gaps. A build and a few unit tests do not substantiate banking settlement, legal compliance or release readiness.
- `modules/physical-operations-cmms/README.md:7` claims feature parity/full feature EAM; app registration lacks listed vendor/customer/request services, scheduled automation/IoT consumer evidence and tests. Module WI-OI-031 actually describes solutions-pack hub, so its exact work-item scope must be clarified.

## Required next evidence before any business-ready label

For each module, obtain an isolated supported environment and authoritative source provenance; execute role-specific UI→API→DB/outbox/provider→visible result scenarios including refresh/restart, retries, concurrency, stale data and dependency failure. Use known synthetic records only in explicitly isolated certification tenants; they establish behavior, not legitimate production value. Independently validate financial and security findings. Full module acceptance requires its stated user outcome, measured business result and named human acceptance, beyond technical pass counts.

Suggested priority: contain/relabel misleading actions and reports, fix identity/tenant boundaries, reconcile ownership and requirements, choose a single complete business outcome, then certify each adjacent module as a dependency of that outcome. Do not delete source or change behavior under this read-only audit.
