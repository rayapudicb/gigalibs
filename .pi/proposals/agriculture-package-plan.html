Agriculture Package Plan

Proposal, not approved Nothing started Aligned to the product vision §3–§8 AI predictions out of scope

Agriculture is built as configuration on top of common modules, not as agriculture code. The common analytics engine comes first. It also serves manufacturing Release 1, so it respects the manufacturing-first decision. The agriculture sources and pack come after it.

Charts hold no dataA chart is a saved query plus a chart template. The same data can be switched to any chart type that fits it.
No developer per requirementAnalysts connect, model, chart and report in the UI. Developers build each layer once, plus one adapter per kind of source system.
Agriculture is a packWording, fields, lists, dashboards and metrics are settings. The only new code is reusable gaps such as piece-rate pay.

How data moves

Pull, model once, query, chart, compose

This is how Palantir Foundry, Looker, Power BI and Tableau avoid a developer for every new question. Each layer is built once and then configured.

sourceFarm systems

farmOS and Farmier, Ekylibre, Tania, weather, market prices

1 connectConnector Hub

one adapter per system type, scheduled incremental pulls, no duplicates

2 modelRecords and measures

standard farm records; measures defined once, like yield per hectare

3 queryOne engine

measure by dimension, filtered by place, crop, season or date

4 visualiseChart templates

24 chart types plus a map; switch type on the same data

5 composeDashboards and reports

saved views with shared filters; scheduled delivery

Every record carries its place. Incoming data is linked to a Geospatial place (Farm › Field › Block) once, when it arrives. Filters then use the place tree, and each user's place scope limits what they can see.

Development plan

Seven phases, common capability first

Phases 1 to 3 are common and serve manufacturing too. Agriculture-specific work starts at phase 4, when you schedule the second industry. Sizes are relative (S, M, L); estimates follow the phase 0 decisions. Each phase is a work item with gates G0–G7, and only one runs at a time.

0

Decisions and registration

Size SOwner

Answer the decisions listed below. Register the work items with G0–G3 recorded, and choose when each starts. The GPT agent holds the active slot until WI-OI-085 reaches Review.

Exit: the decisions are recorded, and phase 1 is registered as the next active item.

1

Complete the Analytics engine

Size LCommonServes manufacturing KPIs
  1. Query. One query contract: measures, one or more dimensions, time grain, filters and place scope. It returns rows, uses safe SQL, and keeps tenant isolation and the accessible data table.
  2. Model. Formula measures such as yield per hectare. Measure versions are published through maker-checker, and each chart keeps the version it was built on. Sensitive measures are flagged.
  3. Speed. Typed fact rows, summaries per measure, place and day or month (refreshed as data arrives), a result cache, and time and row limits. Benchmark at 1M and 10M rows against the agreed target.
  4. Visualise. A chart is a query plus a chart template. One renderer covers all 24 types, a "change chart" menu offers only the types that fit, and there is a map chart. The static chart gallery is removed.
  5. Compose and permissions. Dashboards with shared filters (time, place, category), scheduled CSV reports, seven permissions and four default roles, and every change audited.
  6. Proof on manufacturing data. CMMS work orders by site over time, built with the no-developer test below.

Exit: the no-developer test passes on manufacturing data, and the Wave 1 KPIs (WI-OI-090) can be built on it.

2

Connect: one path for outside data

Size MCommon
  1. Adapter framework in Connector Hub: logins (OAuth2, API key, token), paging styles, incremental pulls, retries, and a quarantine for bad records.
  2. Bridge to Analytics: raw records become datasets through no-code field mapping, including unit conversion (kg, quintal, t).
  3. Scheduler for pulls and report runs.
  4. One connector owner. An ADR makes Connector Hub the integration foundation (plan C10) and retires the copies in Analytics and the core API.

Exit: a REST source syncs on a schedule into a dataset, with no code beyond its adapter.

Can start after 1a and 1b.

3

Places with boundaries

Size MCommon
  1. Area computed when a boundary is saved, and stored on the place.
  2. Records with only coordinates are assigned to the smallest place that contains them. Unmatched records go to a visible "Unplaced" bucket.
  3. Places are created or updated from source locations, keeping each source id linked to its place id.
  4. Each user's place scope applies to every Analytics query. It arrives in the signed context today but is unused.

Exit: a map of fields coloured by a measure, filtered to one farm, shows only what the user may see.

Depends on decision 3 (PostGIS or code).

4

Agriculture sources

Size MAgriculture
  1. farmOS adapter (JSON:API, OAuth2 client credentials). It also covers Farmier, which hosts farmOS.
  2. Weather adapter (provider to choose).
  3. Market price adapter (source depends on country).
  4. Ekylibre adapter (REST with a token) for accounting and profitability.
  5. Tania, only if a client uses it (last change March 2026).

Exit: each source syncs a real farm's data into the standard records, with no code copied from GPL or AGPL projects.

Needs phases 2 and 3.

6

Reports v2: PDF and Excel

Size MCommon
  1. Excel from the same result table, one sheet per chart, with formula-injection protection (reuses the Workforce export pattern).
  2. PDF with charts rendered on the server, the filters applied, data freshness, and a data table under each chart.
  3. Delivery through the existing channels: email, webhook, SFTP, in-app, and signed download links.

Exit: a scheduled report arrives as PDF and Excel that match the screen.

Can run any time after 1e. The plan puts it in Wave 2 (WI-OI-096); decision 6 can move it earlier.

Acceptance

The no-developer test

An analyst does all of this in the UI, with no code change and no deploy. It is run first on manufacturing data (phase 1f), then on a farm (phase 5e).

  1. Connect a source and see its fields.
  2. Map the fields to the standard records, including units.
  3. Define a measure such as yield per hectare, and have a second person publish it.
  4. Build a chart of that measure by field and month.
  5. Switch the same chart to three other chart types without rebuilding the query.
  6. Add it to a dashboard filtered to one farm; a user scoped to another farm sees nothing from it.
  7. Schedule a report of the dashboard to a recipient who is allowed to see it.
  8. Find every step in the audit log and every number's lineage back to its source.

Risks

What could go wrong

  • Licences. farmOS is GPL-2.0 and Ekylibre is AGPL-3.0. Integrate through their APIs only and never copy their code.
  • Messy source data. Missing boundaries, mixed units, fields without crops. Mapping handles units, and the Unplaced bucket keeps gaps visible.
  • Speed at volume. Measured in phase 1c before anything is built on top.
  • Scope creep into prediction. Kept out until D11.
  • Catalogue truth. Agriculture is not advertised as available until it is Certified (vision §5).
  • Two agents at once. Only one active item; the GPT agent is on WI-OI-085f now.
Not in this plan

Later, by decision

  • Yield, pest and disease prediction, and model-based crop advice: AI gateway C11, after D11 (Wave 3).
  • Live soil-moisture and flow sensors: IoT ingestion C10 (Wave 3).
  • Satellite imagery and NDVI indices beyond field area.
  • A general ledger. ADR-0013 rules it out; money figures come from the farm's accounting system.
  • Piece-rate pay for crews: a reusable Workforce capability, when a client needs it.
