## 3. Architecture you must preserve

### 3.1 The target: the owner's product model (vision §3–§9)

- **Layers** (vision §3):
  - **Kernel:** identity, sessions, tenancy, RBAC and policy, settings, the module registry, persistence
    conventions, events and jobs, audit, secrets, health, and API conventions. It stays small, stable and free of
    business logic.
  - **Capability products:** workflow, forms, approvals, notifications, documents, reports, maps, analytics and
    so on. Each one is a complete product, not a set of screens.
  - **Adapters:** vendor-specific behaviour sits behind ports (`ObjectStore`, `PaymentGateway`, …). Modules
    never embed a vendor.
  - **Industry packs:** metadata only (terms, roles, forms, rules, workflows, dashboards, defaults). Never copied
    code.
  - **Experiences:** web, mobile, admin, embedded. UIs are consumers, never the source of business truth.
- **Module product contract** (vision §4). Every module ships:
  - a manifest;
  - a framework-free domain core;
  - versioned contracts;
  - real persistence with tenant scoping;
  - runtime adapters and configuration;
  - complete UI states (empty, loading, error, denied, conflict, recovery);
  - security, reliability, observability and lifecycle;
  - verification, documentation and supply-chain evidence.

  A module never requires edits to another module's source. Cooperation happens only through declared contracts
  and versioned events.
- **Maturity** (vision §5): Concept → UI Prototype → Core Implemented → Integrated Candidate → Certified →
  Production Proven. Only Certified or Production Proven may be advertised as available.
- **Certification** (vision §6): 13 gates:
  1. build and packaging;
  2. contracts;
  3. functional completeness;
  4. configuration;
  5. tenancy and authorization;
  6. audit;
  7. reliability;
  8. upgrade safety;
  9. observability;
  10. security;
  11. performance;
  12. user quality;
  13. documentation.

  Our module conformance suite covers parts of gates 2, 5, 6 and 7 only. It is not certification.
- **Runtime** (vision §8):
  - a modular monolith by default, and a service only when justified;
  - the same contracts work in-process or across services;
  - state changes publish through an outbox;
  - long-running work uses durable jobs and events;
  - deployment profiles define the supported infrastructure.
- **Tenant isolation** (vision §9): an end-to-end invariant covering the API context, data, caches, object keys,
  queues, events, logs, exports, analytics and AI retrieval. Deny by default, least privilege, short-lived
  credentials.

**A request, end to end:**
1. The browser (later, a mobile device session) calls `/api/<gateway>/<path>` on the web.
2. The web checks the user's session with the core API. It looks up the route in the generated gateway table
   (method, path, required permission) and checks the tenant's entitlement for the module.
3. It signs a `PlatformContextV1` with that module's own Ed25519 key. The context carries:
   - audience `gigalibs-<name>-api`;
   - tenant, subject, session and roles;
   - granted scopes, persona, org and spatial scope;
   - the entitlement;
   - a lifetime of at most 300 s.
4. `signed-module-proxy.ts` forwards to `localModuleUpstreamUrl`: the exact module origin, plus `/<name>` for a
   hosted module.
5. The module's guard verifies everything again; the module never trusts the web blindly. `ModuleDatabase` sets
   `app.tenant_id`, so RLS confines every query. Writes record audit and outbox in the same transaction.
6. Other modules learn about changes only through outbox relays and inbox receipts (ADR-0007 option A,
   CMMS ↔ Workforce). Never through a direct import or a shared table.

### 3.3 Invariants: every change must keep these true

- No module imports another module's code or reads another module's schema. Its runtime role is refused on
  other schemas; the 085e proof shows this.
- Module APIs accept only a context signed by the web for their own audience, with the module's own key.
- Every tenant table has `tenant_id`, forced RLS and a tenant policy. Audit is append-only. The API never
  receives the migration/admin database URL.
- Manifests are the single source. Generated files carry a "Generated … Do not edit" header: change the manifest
  and regenerate.
- The web shell has no module-specific hand wiring. A new module needs no shell edit (the Wave 0 exit criterion).
- Solutions contain configuration only, never code.
- The catalogue shows the real maturity. Nothing is called available without evidence.
- No development or self-issued token exchange anywhere. There is one known violation, not yet fixed: the web
  gets E-Signature tokens from `POST <esign>/oidc/dev/token` (`apps/workflow-platform/app/api/esign/[...path]/route.ts`).
  See Task 4e.

### 3.5 Industry packaging (manufacturing, agriculture, any industry)

**Target** (vision §3.4, ADR-0013 §1):
- An industry is a **pack**: metadata only, never code.
- A pack contains terminology, entity schemas, roles and policies, forms, rules, workflows, SLAs, dashboards,
  reports, localisation, adapter selections, and an acceptance suite for that industry.
- A **solution** (`solutions/<name>.yaml`) is configuration only: the selected modules, one industry pack and
  one country pack.
- A new behaviour or object becomes a reusable module, never per-client code.

**The owner-approved design** (`.pi/work/WI-OI-074.md`, G0–G2, paused until the second industry):
- **Four axes on which industries differ:**
  1. **words:** the vocabulary layer;
  2. **data:** governed custom fields, ADR-0002;
  3. **choices:** tenant catalogues mapped to fixed behaviour classes;
  4. **rules and objects:** reusable capability modules and rule packs, never client code.

  Axes 1–3 are configuration a non-engineer can change in minutes.
- **Seven pack layers:**
  1. vocabulary (WI-OI-074);
  2. fields and forms (WI-OI-075);
  3. lists and types (WI-OI-076);
  4. capabilities, screens and personas (entitlements; WI-OI-077);
  5. workflows and hand-offs (Workflow Studio, not yet attached to CMMS or Workforce; WI-OI-078 approval hooks);
  6. outcomes and KPIs (WI-OI-072 / P10);
  7. core rules, which stay in code.
- **Canonical concepts** are mapped across manufacturing, agriculture, hospitality and logistics. The known
  capability gaps:
  - piece-rate pay (agriculture);
  - lots and expiry (logistics);
  - hourly/mileage pay (logistics).

**What exists today:**
- `solutions/manufacturing.yaml`: modules CMMS, Workforce, Geospatial, Analytics and Connector Hub;
  `industryPack: manufacturing`; `countryPack: null`, because D4 is open.
- `solutions/proof-without-cmms.yaml`: the no-CMMS proof.
- Industry packs are 9 JSON files **inside the Workforce module**: `modules/gigaops/config/industry-packs/`
  (construction, event-staffing, healthcare, jp-metro-industrial, logistics, manufacturing, qsr, travel-crew,
  warehouse).
  - Country packs: `modules/gigaops/config/country-packs/` (AU, EU, GB, IN, US).
  - They hold only Workforce wording, role labels, certifications and pay flags.
  - The manifest audit reads them from there.
- **There is no agriculture pack.** CMMS has no pack content: work-order types, failure codes and asset classes
  are enums in code, which WI-OI-076 changes.
- Analytics has its own governed industry and country metric catalogues (WI-OI-064).
- The proof that a second solution needs no code is the facility pack (WI-OI-097, Wave 2). The configurability
  proof WI-OI-063/064 (M1) still needs the owner's blind third-industry acceptance run.

**Divergence (ask the owner, do not decide):**
- Packs live inside one module and cover only that module. The vision's pack spans all modules at the solution
  layer.
- Where packs should live, and when agriculture or another second industry starts, are owner decisions (Task 2d).
- Do not create packs or move them before those decisions.

**Goal:** prove that a module created only by `pnpm module:new` appears in the sidebar and works end to end

**Facts you need:**
- A `PLANNED` or `CONTAINED` module is shown as unavailable (`AppSidebar.tsx` around line 346). It cannot be
  opened: `lib/module-access.ts` `canOpenPlatformModule` requires `AVAILABLE` or `REVIEW`, plus the tenant feature
  and the permission.
- To open the module, a test tenant needs:
  - the module's **entitlement**, set through `PUT /api/v1/platform/tenants/:tenantId/entitlements` on the core
    API (platform owner or admin; `packages/tenancy-nest/src/platform-administration.controller.ts`);
  - its **feature key** in the tenant's features (`verify-gigaops-web-path.mjs` creates tenants with a `features`
    list);
  - a role with `field-inspections:*`.

  The web signs contexts only for entitled modules (`lib/platform-context.ts`).
- So the proof module must be promoted to `REVIEW` through the listing gate, in the throwaway copy only. Use the
  promotion order recorded in `.pi/work/WI-OI-085.md`:
  1. set the readiness;
  2. run `node scripts/module-manifests.mjs --write --conformance-module <name>`;
  3. commit in the copy's throwaway git repository, so there is a source identity;
  4. build and start the images;
  5. run `pnpm module:conformance <name> --live --record`;
  6. run the ordinary audit again, with no bypass.
- The repository must not keep a sample module. Everything happens in a throwaway copy outside the repository.
  `.pi/handoff/proof-scripts/host-proof.sh` shows how to make the copy (tracked plus untracked non-ignored files),
  install offline and clean up. Set `PROOF_WORK_DIR` to an empty temporary directory outside the repository
  before running any of those scripts.

**Steps:**

**Pitfalls already paid for:**
- **zsh:** the Bash tool runs zsh.
  - `for c in "pnpm build"; do $c` does not word-split (exit 127); use `eval "$c"`.
  - `$p[` is read as an array subscript; write `${p}`.
- **Source identity:**
  - Never pipe `refresh-source-identity.sh` into `head`. SIGPIPE kills it half-way, and the image identities in
    `.env.*` go stale.
  - Any untracked, non-ignored file changes the source-state digest, and then conformance L0 correctly refuses
    the image. Keep helper files out of the tree, or remove them before the live checks.
- **NestJS:** shared Nest libraries must declare `@nestjs/common` as a peer dependency. A second copy inside an
  image turns HttpExceptions into 500s. The image checks count copies.
- **pnpm in images:** `pg` in images is a pnpm link (`app/node_modules/pg -> .pnpm/...`). Check the link and its
  target, not `pg/package.json`.
- **Tests:** `pnpm test` reads `@gigalibs/contracts` from `dist`. Rebuild contracts before testing catalogue
  changes.
- **Timing:** do not run live verification while builds or tests load the host. The live scripts sign 120-second
  contexts, and latency assertions fail falsely.
- **psql:**
  - use separate `-c` commands with `-v ON_ERROR_STOP=1`, and check the exit code;
  - stderr and stdout interleave out of order through a pipe.
- **Generated modules:** a generated module above `PLANNED` needs a passing live conformance record for its
  current fingerprint (listing gate). Follow the promotion order exactly.
