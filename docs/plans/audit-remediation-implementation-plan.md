# GigaLibs business completeness and production implementation plan

Date: 2026-09-09. Planning work item: WI-OI-037. Audit: WI-OI-036. Status: proposed implementation sequence, ready for plan review; no module acceptance, feature implementation or release authorization is recorded by this document.

This plan answers four questions for every capability: what useful outcome it owes a user; where that outcome currently breaks or remains unproved; what to repair or extend; and what observable evidence permits release. It contains 98 planned submodule slices across 18 business/platform groups, including all 11 business-module directories, and a separate 206-entry package register. The target is complete, operable business workflows within an explicitly accepted product scope. “Every module is 100% ready” cannot be inferred from this plan or a test count.

Until answered, their country/provider-dependent acceptance cases are explicitly unverified; no global tax/e-invoice, banking, safety or legal-compliance promise is made. ## 2. How incomplete functionality is evaluated

For every role and action, trace: outcome → UI/control → authenticated API → permission/object/tenant checks → validation/policy/version → domain command → authoritative database transaction → outbox/job → actual consumer/provider → receipt/reconciliation → refreshed UI → audit/telemetry → measurable business result. A broken mandatory link makes that action incomplete.

| Evidence state | Meaning | Implementation response |
| --- | --- | --- |
| Runtime verified, bounded | Specific scenario passed against named source/artifact/environment | Retain evidence; run affected regression checks after changes. Do not generalize it to an entire module. |
| Proven broken or fabricated | Source or execution demonstrates incorrect behavior; evidence type is recorded | Repair/contain before live use. Never keep a fake completed state as a fallback. |
| Implemented but incomplete | Some required lifecycle, role, persistence, failure or recovery link is absent | Extend the existing owner through the missing links. |
| Present but disconnected | Producer, API, UI, record or package exists without a demonstrated consumer/outcome | Connect it through a reviewed contract, or explicitly revise the product scope. |
| Missing | A required capability has no implementation found in the searched scope | Implement after confirming the requirement and checking for reusable existing code. |
| Unverified / blocked | Implementation or evidence may exist, but no adequate test was run or a dependency is unavailable | Inspect and test first; avoid rewriting potentially working functionality. Record the exact blocker. |
| Not applicable | Not required for the accepted release profile, with an explicit reason | Exclude from claims and runtime reachability where necessary; retain the decision and revisit if scope changes. |

The backlog separates three kinds of additions:

1. **Required completion:** already required by the approved/accepted outcome; e.g. invoice payment allocation and corrections are necessary to complete the FR-17 receivables lifecycle.
2. **Proposed necessary extension:** inferred from a demonstrated business break; e.g. a reconciliation work queue with owners so staff can resolve provider uncertainty. Record the assumption, affected users, policy and acceptance criteria; Product confirms scope before the dependent Build slice.
3. **Demand-led extension:** useful only for a selected segment, country, deployment or pilot; e.g. corporate card issuance, advanced hedging, additional ERP adapters or fleet routing. Do not implement merely because a package or button exists. If already sold/accepted scope, it becomes required completion rather than optional.

An extension must name the user, current failure/workaround, intended terminal result, source/data owner, permissions, downstream consumer, maintenance cost and metric. If these cannot be stated, it is a discovery item. Prefer completing an existing module, choosing one supported adapter or integrating a proven owner over inventing another service/table.

Examples: an invoice list is incomplete for receivables if payments cannot be allocated; a persisted REIMBURSED label is incomplete without receipt and reconciliation; a rule verdict is valid computation but not evidence its suggested action executed. A hash proves consistency with bytes, not that the claimed signature, payment or business event happened. Pure calculations do not need arbitrary database writes; persisted business facts and derived outputs need traceable authoritative inputs and versions.

## 3. Common engineering work required for each planned slice

Every row below inherits this complete delivery contract. The CSV includes it as `COMMON`; it cannot be dropped because a row discusses only a business rule.

- **Requirements/design:** actor, expected outcome, negative examples, FR/NFR and owning WI; compare existing APIs/tables/jobs and document one authoritative owner. Review contracts and threat/data-flow changes before Build.
- **API/UI:** versioned bounded inputs, tenant/object permissions, idempotency, optimistic concurrency, stable errors, cursor pagination and authorized exports. Loading/empty/partial/stale/denied/conflict/failure/retry/success must reflect confirmed server state. Shared app and standalone UI must use the same authoritative business owner.
- **Data/migrations:** real PostgreSQL persistence where state is required; tenant-safe constraints and indexes; atomic financial/state changes; expand/backfill/verify/switch/contract migrations; compatibility, clean install, upgrade and recovery evidence. No modification of deployed migrations or automatic deletion of unknown records.
- **Provider/jobs:** scoped non-returning secret references; bounded timeout; classified transient/permanent failure; retry/backoff and circuit policy; durable idempotency/intent; provider receipt and unknown-result reconciliation; outbox/inbox, dead-letter handling, retry limits and operator recovery. Compensation is a real permitted business action and may fail; it is not a universal rollback guarantee.
- **Evidence/operations:** correlated audit/logs/metrics/traces, health/readiness and source freshness; retention/hold/export controls; meaningful domain, contract, real-infrastructure, security, E2E, migration and recovery tests; updated operator/user documentation and independent review.
- **Result:** the user completes the real workflow; refresh/restart/retry/concurrency do not lose or duplicate confirmed effects; the result can be independently reconciled. Tests and demo records are isolated and excluded from customer value/billing metrics.

### Data legitimacy repair before trusting reports

Snapshot and classify affected data without destructive cleanup. For each source/derived record, capture tenant, source account/object/version, authority to ingest, source time, ingestion event, classification, transformation version and business owner. Distinguish verified source/manual evidence, verified derivation, unverified origin and isolated synthetic data. Persisting a fabricated record does not make it verified. Backfill must default to unverified, never silently trusted.

Reconcile known fake receipts, completed runs, recovered amounts, seeded companies and inferred metrics with actual source/provider records. Route unresolved cases to a controlled investigation queue and exclude them from claimed outcomes. Finance/owners decide corrections through audited reversals or governed corrections; retain original evidence and applicable holds. Validation of unknown customer data is a separate evidence task from testing software with safe generated fixtures.

## 4. Delivery order and release profiles

Only one implementation module is in Build at a time. Discovery, independent QA and documentation may overlap; dependent code changes remain sequenced. The orchestrator reconciles the current tracker before activating a Build item. This plan does not move every module into Build or assign new feature priorities as accepted decisions.

| --- | --- | --- |

| S1 — trust boundary | IAM-01/02 plus only the identity/routing/data controls required by the selected release profile; other IAM slices run when their accepted outcome requires them | Invalid login fails closed; direct APIs enforce principal/tenant/object scope; fake execution and seeded fallbacks cannot be reached in candidate profile. Independent security review. Full marketplace/SSO productization is not a hidden prerequisite for standalone AR. |
| S2 — complete AR first | AR slices in their listed order: empty setup → customer/draft/issue → document/delivery → manual receipts/allocations and reconciliation → hosted provider/reconciliation if accepted launch scope → corrections → aging/collections → required metering/export/operations | Candidate for a specifically accepted standalone or suite AR launch only after all its G5/G6 gates. Minimal supported tax/currency policies/providers serve AR without building an entire tax/treasury suite. |
| S3 — close the AP automation outcome | CN → DS → RL → WF, including action/event/recovery infrastructure as needed; AP/exception/value slices | Authorized source → validated invoice/PO/receipt → explained decision → approval → actual ERP hold/posting → receipt/reconciliation → defensible value. Each dependency reaches Review before another enters Build. |
| S4 — spending and financial extensions | Spend → required tax/FX depth for the selected customer scope → recovery; reuse S3 boundaries | Expense-to-reimbursement and evidence-to-recovery outcomes. Advanced tax/FX demand can change this sequence through explicit prioritization. |
| S5 — physical operations | CMMS → necessary spatial/source/rule integration | Request/reading → planned/assigned work → parts/labour execution → verified closure/cost; first prove a bounded maintenance operation. |
| S6 — productization and additional capabilities | Remaining usage/catalogue/solution/AI/document/map/demo work according to validated release demand | A paid suite release requires its entitlement, metering, billing and operational controls before charging. No calendar or effort percentage is invented. At each G2/G3 exit estimate its vertical slices using the confirmed adapters, migrations, test environments, workload and available owners. A single module can go live after its complete scope is accepted; that does not certify the whole suite. Any excluded feature must be accurately described, technically inaccessible where unsafe, and explicitly accepted as outside the release; hiding an accepted requirement is not completion.
