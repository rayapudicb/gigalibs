# Frontline mobile suite: architecture and implementation plan

**Status:** Owner-approved direction (2026-10-30); boundary review and deploy slot open · **Work item:** WI-OI-132 · **Scope:** 12 product specifications in `docs/products/mobile-suite/`.

This plan governs implementation interpretation of the 12 specifications. Their outcomes and journeys remain product goals. Their §6 diagrams, table names, event topics, route names, technology choices and regulatory claims are **proposals**, not evidence of implemented contracts. Validate each against the running module before coding. The pasted summary's blanket claim that all 12 are already architecture-aligned is not supported by the repository.

## 1. Programme boundary and sequence

The 12 entries are **mobile-first product experiences on a separate planning track**. Mobile-first applies to **all** GigaLibs modules: each relevant module needs a task-focused mobile journey as well as its admin/configuration web surface. These 12 provide additional frontline journeys and do not substitute for the mobile work in the other module cards. They are not automatically 12 new deployable modules, and the owner's earlier 19-module list is not silently expanded to 31. That 19 count is a historical architecture snapshot: the execution plan v3 counted 37 generated catalogue entries and 25 manifests on 2026-10-13; this checkout has 29 `modules/*/module.yaml` files. These are different inventories, and neither count certifies a running module. Reconcile the current generated catalogue, manifests and runtime profile before assigning new catalogue entries. A product may add capability to an existing owner, or require a new bounded context. A new runtime module needs the ADR-0016 catalogue, entitlement, manifest and certification decisions. None of these 12 is certified by the existence of a spec or product lead agent.

The owner's fixed deploy sequence remains unchanged. This track has **no assigned deploy slot**. Design and contract reconciliation may happen now; build starts only through approved, separately scoped work items when prerequisites and the owner's sequence allow it. The owner deploys from a release worktree and accepts each journey.

**Within each full product/module build:** (1) approve ownership and contracts, (2) implement migrations, domain APIs, events and tests, (3) implement and verify admin UI/configuration, (4) implement mobile UI and offline behavior against those contracts, (5) run the full module gate and `pnpm verify`, then make the module-completion commit. This honors the requested backend/admin-first build order. A global pass that builds all 12 backends and admin screens, stops, then starts all 12 mobile UIs conflicts with the current rule to finish and commit each full module before stopping. It needs an explicit owner rule change; this plan does not assume one.

## 2. Architecture decisions to use

| Concern | Decision for this suite |
| --- | --- |
| Authority | One domain owner writes each record. The control plane owns identity, tenants, roles, entitlements, organization and governed settings. CMMS owns assets, work orders and maintenance requests; Workforce owns people, shifts and assignments; Inventory owns balances and reservations; Product Catalogue owns product definitions; Geospatial owns places; Communications owns messages. Proposed new owners below need an ADR before schema creation. |
| Data boundary | Mobile calls the existing `/mobile/v1` BFF over HTTPS. The BFF validates identity and scope, composes or routes authorized requests, and never writes module tables. A module writes only its own database in a local transaction. No cross-database foreign keys or direct writes. |
| Cross-module action | Use versioned contracts and the accepted module-owned transactional outbox, authenticated relay and inbox receipt pattern (ADR-0007). Transport is replaceable; `@gigalibs/broker`, Kafka/RabbitMQ and specific topics in the specs are not approved dependencies for this track. Define retry, ordering, poison handling, operator recovery and reconciliation for each action. |
| Scope | Tenant comes from validated session/signed context, never client-supplied `X-Org-Id` or `X-Roles`. Organization ownership and separate place scope follow ADR-0018. Server-side object, action and field checks apply to admin, BFF, mobile, jobs and sync. |
| Admin/config | Reuse published Configuration Studio/Application Dictionary manifests and typed domain adapters (ADR-0033). Define version, effective date, maker-checker, rollback and audit for policy/template changes. Specialized builders may be custom components, but saved configuration is governed and server validated. |
| Mobile | The v1 BFF currently covers sign-in/session and read-only windows; product write, media and sync endpoints require new reviewed contracts. Derive mobile fields/actions from approved domain and metadata contracts. Capture only the minimum data needed for a journey, with loading, denial, conflict and recovery states. |
| Offline | SQLite is a device cache/command queue, partitioned by tenant, user and installation, encrypted and purged on logout, revocation and workspace switch. Server remains authoritative. Every queued command needs a stable client operation ID, actor, scope/config version, timestamps and replay result. A stale or changed policy must produce an explicit conflict, never silent acceptance. |
| Evidence | Product outcome percentages, 5–10 second targets, anti-tamper guarantees, ISO/FDA/OSHA claims and hardware support are hypotheses until measured or independently reviewed in the target environment. No compliance label is inherited from eSignature or a QR/NFC scan. |

## 3. Proposed ownership and product contract map

The owner approved the principle of reusing existing domain owners, adding bounded contexts only for uncovered concepts, and building backend/admin before mobile inside each complete module. This map remains subject to the [suite boundary ADR](../architecture/ADR-0035-frontline-mobile-suite-boundaries.md) and independent review. Product code identifies the experience/entitlement; the owner column identifies the proposed writer. A shared runtime service is permissible where one bounded context owns several products, but each product still has its own requirements and journey proof. Named tables and endpoints remain unverified.

| Product | Proposed authoritative writer | First backend/admin contract | Mobile and integration dependency |
| --- | --- | --- | --- |
| **M-RND** Rounds | New Frontline Operations context for route versions, route-specific roster references, assignments, readings and exceptions. Workforce retains the worker and shift roster; CMMS retains meters/work orders. | Route/checkpoint definitions, schedule window, versioned operator references, thresholds, scope, exception review and published version; command/API for reading and route completion. | Offline route bundle and idempotent readings; explicit CMMS meter/WO requests via relay; Workforce eligibility uses a signed request, not a DB join. |
| **M-LOG** Shift log | Workforce M-WF3 owns shift handover (plan v3 and WI-OI-108); the owner of operational notes and bypass facts must be reconciled with that handover record before any new table. | Log taxonomy, shift-bound board, bypass rules and two-person handoff state graph. | Offline draft capture; handoff acceptance and safety-sensitive state change require current authority and conflict check. Safety alert is a consumer contract. |
| **M-CAL** Calibration | CMMS maintenance extension for instruments, standards, procedures and results, unless inventory proves an existing calibration owner. | Standards validity, tolerance/profile versions, as-found/as-left math, certificate approval and PM linkage. | Offline capture with immutable raw readings; server recomputes. Signature workflow needs reviewed identity, re-authentication, intent and records; no automatic 21 CFR Part 11 claim. |
| **M-LOTO** LOTO/PTW | CMMS M-CM2 owns permits under plan v3/WI-OI-108 and owns the WO interlock. Do not create a parallel Safety permit store; reconcile its safety policy with SPEED without moving SPEED's screening records. | Permit/lock/isolation procedure, authorization, expiry, conflict matrix, emergency override and audit/reconciliation. | Offline draft/evidence only. Activation, release and CMMS interlock require online authoritative validation and fail closed on stale/missing permit state. IoT suppression is a separate reviewed rule, never implied by permit creation. |
| **M-INC** Hazard/incident | Proposed Safety Operations incidents owner; CMMS owns remediation WO. | Hazard taxonomy, triage, RCA, classification, corrective-action policy, retention and restricted access. | Offline report capture with evidence upload/retry; event to CMMS/notifications after triage rules. Statutory reports need jurisdiction-specific legal review and data completeness. |
| **M-DVIR** Equipment check | CMMS fleet/asset extension for inspection and grounding state; Workforce owns credentials. | Check templates by asset class, defect severity, red-tag rule, mechanic clearance and credential-check policy. | Offline inspection capture; **clearance and dispatch eligibility** need server authority. CMMS WO request is idempotent. Do not equate `asset_downtimes` with a grounded-state model without schema proof. |
| **M-CONTR** Contractor pass | Proposed Safety Operations site-access owner; Business Partner/Procurement own vendor identity, Workforce owns worker credentials if applicable, Geospatial owns place. | Induction, insurance evidence, host/escort authorization, access window, evacuation roster and retention. | QR/pass verification and entry/exit require live revocation/status checks or an explicit bounded outage policy. Billable hours go through a reviewed source contract; `spend-management.contractor_hours` is not verified. |
| **M-CHAT** WO chat/PTT | Existing Communications module owns conversations, messages, retention and media references; CMMS owns WO and its reference/projection. | Channel policy, membership/shift rules, moderation, retention, media limits and incident export. | Mobile message/voice flow after scoped authorization. Live PTT/WebRTC is a separately costed capability with network, recording and failure design; basic chat does not certify it. |
| **M-REQ** QR requester | CMMS owns maintenance request intake and conversion; public gateway/BFF handles anonymous capability. | Request taxonomy, rate/abuse controls, duplicate triage, tenant/site asset resolution, consent and privacy policy. | Mobile web form. QR must carry a signed, revocable, scoped capability or equivalent; no trusted tenant from the QR alone, and no unrestricted anonymous write. Status updates require proof of requester control. |
| **M-SOP** Visual SOP | CMMS owns maintenance job plans/manuals (EAM-003). A broader operating SOP and execution record may belong to Frontline Operations only after the existing Documents/Knowledge capability is reconciled; no duplicate maintenance SOP store. | Author/review/publish/retire, conditional step schema, media validation, revision and execution evidence. | Offline published bundle and step queue; reject unknown/withdrawn safety-critical revision, and show conflict recovery. CMMS updates via explicit command/event. |
| **M-TAG** Commissioning | CMMS owns asset creation/commissioning; Geospatial owns places, Product Catalogue owns model/product matching. | Draft intake, duplicate/serial review, asset class/hierarchy mapping, place reference, approval and audit. | OCR is assistive and must be confirmed; NFC write failure must not create a second asset. Device tag, CMMS asset and place association reconcile via IDs and retry. |
| **M-BOM** Visual spares | CMMS owns asset-specific diagram/hotspot-to-part mapping if no existing engineering-content owner; Product Catalogue owns parts, Inventory owns ATP/reservations. | Governed diagram revisions, part equivalence, hotspot mapping, WO linkage and low-stock policy. | Cached diagram; live ATP clearly marked with freshness. Reservation is an Inventory command with idempotency, available quantity and WO reference; procurement replenishment follows Inventory's approved event/contract, not a mobile direct write. |

Before a schema is designed, produce a one-page **ownership record per product**: entity and writer, existing table/API evidence, classification/retention, organization and place policy, permission matrix, lifecycle/invariants, cross-module reference, outbox/inbox contract, migration/roll-forward and conflict policy. Reuse an existing owner whenever its business meaning and security controls fit. A proposed new context becomes an actual module only through an ADR and module catalogue decision.

## 4. Design order and required artifacts

1. **Reconcile current state.** For all 12, compare spec §6 with actual module manifests, APIs, migrations, BFF routes and runtime status. Build an API/data gap register; record which requested feature already exists, is partial, or is absent. Treat the 12 agents as product roles, not evidence of 12 running modules.
2. **Set module boundaries and journeys.** Approve each writer, state transition, actor and cross-module effect. Map every journey to FR-01–FR-16 (and FR-17 only where billing applies), NFRs, a named requirement, ADR and later test/release evidence. The owner approved reuse-first direction; the boundary ADR must reconcile CMMS M-CM2 permits, Workforce M-WF3 handovers and CMMS maintenance SOPs before sizing any new Frontline Operations or Safety Operations context.
3. **Design data and migration.** Start from domain invariants, not UI fields. Specify PostgreSQL tables only in the owner schema: tenant and owning-unit keys, place reference, constraints, RLS, append-only evidence where needed, indexes, version columns, idempotency receipts, audit and outbox. Include clean install, supported upgrade, backfill/compatibility and roll-forward proof. Media uses classified storage references and lifecycle controls, never unbounded blobs in JSON.
4. **Design contracts before UI implementation.** Publish versioned module API and mobile BFF contracts: method/path, request/response/problem codes, permission, object scope, pagination, `If-Match`, idempotency, media upload/download, sync batch limits, dedupe, retry, conflict and result lookup. Define events with producer/consumer, schema version, causality, ordering and reconciliation. Generate clients and contract tests from the approved definitions.
5. **Build backend and admin first.** Implement domain service, migrations and real-PostgreSQL proof. Add Configuration Studio contributions, admin builders, setup wizard/checklist, maker-checker publication, previews, effective dates, permission/audit and recovery. Admin UI uses the same domain API; no local-only business state or parallel CRUD. Verify one configured journey through API and admin UI before mobile coding.
6. **Build mobile against proven contracts.** Map the approved task flow to a mobile state chart; test gloved/thumb reach and representative devices. Implement cache/download, command queue, media upload, sync replay, conflict/denied/expired/revoked states, accessibility and performance. A successful tap is not proof of server acceptance; show pending, accepted and failed states distinctly.
7. **Close the whole module.** Run unit, contract, negative authorization, migration, real-DB, offline/reconnect, duplicate/reorder, BFF-to-module and admin-to-mobile journey tests. Run `pnpm verify`; do not call it Built or commit until the whole product/module card is complete. Record owner-led UAT and security findings by the repository's current release rules.

**First complete build (owner approved 2026-10-30):** WI-OI-133 implements M-RND as its own module, exercising admin route publication, Workforce eligibility, CMMS action, offline sync and Analytics without a life-safety activation. The build card proposes delivery after fixed group 12. Product code and native mobile work are authorized for this module; no deploy is authorized for an agent.

The [M-RND user journey and screen map](operator-rounds-user-journey.md) shows what administrators, operators and supervisors will see, the action on each screen, the real API owner and the remaining gaps. Its product outcome percentages and checkpoint-time target remain hypotheses until representative user/device tests and operational evidence establish them.

## 5. Shared admin and mobile foundation requirements

| Shared capability | Admin/API design to finish before product mobile UI | Mobile proof |
| --- | --- | --- |
| Entitlement and navigation | Tenant enablement, product permission catalogue, scoped role assignments, published manifest and unsupported-feature refusal. Existing mobile session currently has no product module grants. | Only entitled actions appear; every hidden action also fails at the server; revocation removes cached access. |
| Settings | Per-tenant/unit/site policy with defaults explicitly chosen by admin, draft → review → publish, version/effective date and rollback history. | A command records its policy version; stale offline commands receive a governed decision. |
| Sync | BFF write/sync contract and module idempotency receipts, per-command result, ordering, bounded batch and media staging/commit. | Repeat, out-of-order, app reinstall, user/tenant switch, expired session, denied scope and low storage do not lose or leak data. |
| Evidence | Classified media with access control, malware scan as needed, hash, retention/hold and signed delivery URLs; audit actor/time/device and source. | Offline media is encrypted, uploads resume, and orphaned uploads are reconciled. |
| Interlocks | Domain API owns hard stops (permit, red tag, credential, signature). A projection's freshness/lag rule is explicit. | Offline UI never claims an interlocked action succeeded before server acknowledgment. |
| Operations | Per-module health, backlog/age, dead letters, sync conflicts, media failures and reconciliation report with owner runbook. | Pending/failed work remains visible and recoverable to the user or authorized admin. |

## 7. Approval points and Definition of Ready

**Owner direction recorded 2026-10-30:** reuse existing owners first; consider new Frontline Operations and Safety Operations contexts only for uncovered concepts; backend/admin first *inside each full module build*; M-RND first as WI-OI-133. This is not a declaration that all 12 boundaries or safety controls are certified. Existing plan-v3 assignments to CMMS M-CM2 permits and Workforce M-WF3 handovers take precedence over this plan's earlier draft.

**Still open:** the WI-OI-133 post-group-12 delivery slot needs release scheduling; Architecture and Security must review the [boundary ADR](../architecture/ADR-0035-frontline-mobile-suite-boundaries.md), especially the residual new contexts, life-safety interlocks and public QR access. Named humans retain safety, regulatory and release acceptance. No global backend-first override was requested or approved.

An implementation card is ready only when its writer, existing-vs-new module status, dependency versions, permission and scope matrix, data model/migration plan, API/events, admin setup, offline policy, UI states, failure/reconciliation behavior and acceptance journey are concrete. WI-OI-133 records the approved M-RND build; the other products remain planning items until their cards are approved.
